# 长时间运行后代理失效与整机网页断网

用户提供 `Desktop.zip`，包含 2026-09-16 至 2026-09-19 的环境和代理日志。9 月 19 日下午连续 138 次检查均为心跳超时、打开微信失败、不可用；第 137 次于 16:06:54 结束。用户确认微信仍登录，浏览器报 `ERR_PROXY_CONNECTION_FAILED`，系统代理为 `127.0.0.1:5202`，关闭并重新开启同步助手可恢复。

## 已证实的机制

代理日志包含 Windows `AcceptEx` 的 WinError 64、`asyncio.proactor_events.loop` 和 `accept_coro` 异常。当前打包解释器为 Python 3.12.0rc3：`BaseProactorEventLoop._start_serving` 遇到接收连接的 OSError 会关闭监听 socket，而 mitmproxy 的主任务和线程可以继续运行。`ProxyManager.running` 因此仍为真，但新浏览器连接被拒绝。此行为也记录在 [CPython issue 93821](https://github.com/python/cpython/issues/93821)。

通过向真实 Windows Proactor 的下一次 accept 返回值注入 OSError(64)，已复现与用户日志相同的调用栈、端口失效及线程仍存活状态。另通过真实代理关闭监听端口、保留工作线程的方式验证恢复。

日志中的系统错误早于最终心跳中断，不能证明某一条 WinError 64 恰好触发了最终故障，也没有证据表明存在固定的 24 小时到期定时器。网络重置为何在该电脑发生，现有日志不能唯一确定。修复针对已证实的故障机制及网络被失效代理持续接管的问题。

## 原恢复逻辑的两个缺口

`2026.09.17.1` 已包含按环境检查触发的 HTTP 健康探测和重建，`.2` 主要增加版本展示。不能将问题简单归咎于使用 `.1`。

1. 恢复依赖任务进入环境检查。没有任务、任务暂停或正处于上传等其他阶段时，代理没有独立巡检，故障可能持续影响全局网页访问。
2. 恢复冷却期内再次断连时，原逻辑先抛出“稍后重试”，没有先关闭指向故障监听器的系统代理。

这两个缺口均新增测试，修复前测试失败。用户日志未出现 `.1` 应有的健康检查事件，实际运行包与日志的对应关系仍无法仅凭提供的文件确认；本次直接核对修复包的冻结模块并运行其 EXE 验证。

## 修复

- 独立 OS 线程每 5 秒探测本机 HTTP 响应，探测超时 1 秒，与业务任务和前端轮询无关。
- Windows accept 故障、代理工作线程意外退出主动唤醒巡检。异常钩子在 mitmproxy 的 running 阶段安装，避免被 Master.run 覆盖；保留原始异常日志。
- 确认故障后，先关闭系统代理，再执行冷却判断和工作线程退出等待。重建失败时保持系统代理关闭，由巡检自动重试。
- 新监听器必须返回当前实例的 HTTP 标记后才接管系统代理；每次启动生成新标记。
- 自动重建与人工启停共用生命周期锁。主动停止取消巡检；新一轮启动使用独立取消事件，旧巡检不能重新拉起代理。
- 仍需真实视频号页面心跳才能继续采集，不伪造连接就绪或采集数据。

## 验证方法与边界

`venv312/Scripts/python.exe scripts/run_monitor_tests.py tests/test_proxy_lifecycle.py -q --disable-warnings`

覆盖真实 Windows accept 故障、后台退出、无任务时端口失效、冷却期再次失效、重建失败后自动重试、事件循环卡住、主动停止取消恢复、重复启停和连续故障后的线程回收，以及普通网页 HTTP 与 HTTPS CONNECT 转发恢复。测试替换系统代理和证书修改边界，使用临时数据及本机测试服务器，不触碰真实采集、上传和数据库任务。

这些是可重复的故障注入验证，并非真实运行满 24 小时的证明。操作系统仍可能产生连接重置；目标是自动恢复并避免持久的全局代理断网，而不是承诺任何网络条件下都没有瞬时连接失败。
