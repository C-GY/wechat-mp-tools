# 重装后重复上传 OSS

## 问题与复现

旧实现把成功地址写入安装目录下的 `data/channels_parsed_feeds.json`，
任务记录写入同目录的 `oss_upload_tasks.json`。OSS 凭据虽已放到用户目录，
成功上传记录却没有独立的持久索引。新建队列只检查传入作品的 OSS 字段，
不查询历史成功任务；竞对监测还有远端检查，但其他同步入口并不统一使用它。

在隔离环境中调用真实队列和 OSS 上传实现，只替换下载与 HTTP 边界：
同一作品完成 PUT、HEAD 校验、公开读取校验后，清除任务列表，
更换安装数据目录，保持同一用户配置、作品 ID、时间与桶不变。
第二次同步仍执行 DOWNLOAD、PUT、HEAD、GET；串行与并发均可复现。

执行 `venv312/Scripts/python.exe scripts/run_monitor_tests.py tests/test_oss_receipts.py -q`，
修复前两个重装用例均失败，报“同一已验证作品不应再次下载或上传”。
保留安装目录但给队列传入不带 OSS 字段的新采集数据，也存在重复上传路径。

上述证据说明缺少持久索引及统一查询确实是问题；没有证据认定用户的
覆盖安装必然删除了旧数据，也没有修改安装器来假定或掩盖这一点。

## 修复行为

- 独立 SQLite 缓存：`%APPDATA%\Fandow\SelfMediaContentCollector\oss_upload_receipts.sqlite3`。
  文件与凭据分开，清理任务列表或重新配置凭据都不会删除它。
- 以 OSS endpoint、bucket、对象前缀、稳定作品 ID 查询成功记录。
  保存真实对象路径和 URL，采集时间缺失或变化不影响复用。
- 串行和并发队列在下载前查询缓存；命中后回填当前作品数据，任务为
  `skipped`，标注 `reuse_source=local_cache`，不发起下载、PUT 或远端探测。
- 新上传必须完成现有上传与访问校验才写成功记录。先提交独立缓存，再
  回填作品 JSON；后者失败不丢失已确认的上传结果。
- 应用启动时自动补录当前安装中仍可读取的成功任务及作品记录；创建队列、
  清理任务历史前也补做迁移。根据成功 URL 推导原桶，不用当前配置猜测。
  不迁移失败任务、无效地址或不匹配的作品，不用旧记录覆盖已有新回执。
- 缓存保存使用 SQLite 事务、独立连接与唯一键，无任务列表的条数截断。
  缓存读写异常不会静默按“未上传”处理；启动迁移异常记录日志，下一次同步重试迁移。

现有作品明确带有可用 OSS 地址时，保留原先直接复用该地址的行为。
桶隔离针对独立缓存查询，避免将其他桶的历史缓存误用到新配置。

## 验证与边界

22 个针对性回归用例通过，覆盖串行/并发重装、清空历史、新采集数据、
缺失时间、桶/endpoint/前缀变化、校验失败、作品文件写入失败、旧记录迁移、
旧记录不覆盖新对象、远端复用写入缓存及后续免探测。
测试隔离配置目录和安装目录，并在网络边界记录实际传输调用。

OSS、品创、竞对监测、采集完整性及分页恢复相关整组回归最终通过：
184 项测试、58 个子测试，耗时 14.55 秒；源码编译与差异空白检查通过。
首次整组运行中一个并发用例超过了测试设定的 5 秒线程等待时间；
随后单独运行该组 8 项全部通过，整组重跑也全部通过，该用例耗时 0.97 秒。
未通过放宽测试超时规避该现象。

这是同一系统用户的数据缓存。此前若已删除旧成功记录，不能凭空补回；
现有竞对监测的远端校验仍可补录确认存在的对象。更换系统用户或手动删除
该缓存不属于“同一用户重装后保留”的保证。缓存复用也不证明远端对象在
后来被人工删除或移动后仍然存在，与已有 OSS 地址的复用语义一致。
